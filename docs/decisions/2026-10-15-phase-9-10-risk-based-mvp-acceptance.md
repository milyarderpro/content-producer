# CR-020 — Risk-based MVP acceptance and production cutover

- **Status:** Accepted
- **Date:** 2026-10-15
- **Authority:** The owner asked to apply the testing and MVP-completion recommendations after reviewing the prior Viral Producer plugin's isolated test profile, per-case acceptance records, and read-only production cutover smoke.
- **Baseline:** CR-019 on draft PR #6, branch `codex/phase-8-verification`, commit `29772888aba1c0ac7325283c1eda47da461e4829`.
- **Supersedes:** CR-019 only for the ambiguous manual non-owner requirement, manual scenario size, duplicate full-suite execution, and the distinction between controlled pilot readiness and final MVP completion. CR-018 remains historical where CR-019 already superseded its Phase 8 gate. No database, RPC, MCP tool, editorial, or authorization contract changes.

## Reason

Viral Producer uses an [isolated GitHub test branch and private test plugin](https://github.com/milyarderpro/viral-producer/blob/main/docs/test-plugin-installation.md) for mutative acceptance, [records a result for each case](https://github.com/milyarderpro/viral-producer/blob/main/tests/acceptance-tests.md), and runs a short read-only smoke after updating the production plugin. This separation is useful, but a GitHub branch alone cannot isolate Content Producer's hosted Supabase database: two plugin versions could still point at the same database. Content Producer already has deterministic database, authorization, and 33-tool tests that can run against an ephemeral local Supabase stack in GitHub Actions. Its single-owner production environment also cannot prove cross-owner denial manually without a second authorized identity. The MVP needs representative installed-plugin evidence without making the owner repeat the technical suite in ChatGPT.

## Decision

1. **One backend release-candidate technical gate.** Freeze the exact backend code, migrations, configuration, and proposed deployment SHA before the first production write. Run one GitHub Actions gate on that SHA: locked dependency install, one clean local Supabase reset, `pnpm run test-all` (including its `check`, migration-name, MCP, and database suites), applied/source migration verification, local security advisors and catalog/RLS/grant audit, MCP Inspector's 33 valid/invalid/auth paths, and `git diff --check`. Record the SHA, commands, results, and duration. Do not run `pnpm run smoke-test` in the same gate when it repeats the database suite already covered by `test-all`. If backend code, migrations, or security configuration changes, run focused tests during repair and repeat the full gate once on the new final deployment SHA. A docs-only commit after the freeze changes the Git SHA; freeze documents before the gate or rerun it on the new proposed deployment SHA. Do not declare the Phase 9 production gate complete from an old or partial run.
2. **Deployment and hosted boundary.** Phase 9 may prepare documentation and configuration before the gate, but production migration, secret/configuration write, and Edge Function deployment wait for the gate and owner-controlled target confirmation. After deployment, verify `/health`, MCP initialize/list, OAuth/PKCE/resource context, owner access, unauthenticated denial, migration history, production RLS/privileges, and a limited read-only smoke. Perform a safe, owner-approved write pilot only after those checks. Keep rollback and backup evidence. A test-only GitHub branch or plugin is not a substitute for an isolated Supabase project. The final `plugin/mcp.json` may be generated after the production custom MCP connection succeeds in Phase 10. If only package/skill metadata changes while the deployed backend SHA remains unchanged, validate the package and affected MCP/skill tests plus the relevant manual cards; reuse the recorded backend gate without rerunning the database suite. Record both the backend deployment SHA and final plugin package SHA. A backend/security change invalidates that reuse.
3. **Cross-owner evidence.** Keep owner isolation and non-owner denial mandatory. Prove them with automated authenticated non-owner tests against ephemeral local Supabase and through the server/RPC boundary; verify the production unauthenticated boundary during hosted smoke. A production non-owner test is optional only if a separate authorized test identity safely exists. Remove non-owner denial from the owner's mandatory ChatGPT manual cards. Do not mark the security criterion passed without deterministic evidence.
4. **Installed-plugin manual scope.** Phase 10's guide contains exactly 11 numbered scenario cards, `MAN-01..MAN-11`, each with a fixed prompt or short prompt sequence, setup, expected tool/behavior, forbidden result, simple state check, and recovery. The owner executes the cards once in ChatGPT with the final installed plugin; rerun only failed or affected cards after a fix. The AI prepares the cards, checks redacted evidence, and runs technical tests. The 101 frozen prompts remain a regression inventory, not an MVP live gate. The manual cards test the following outcomes:
   - `MAN-01` connection, OAuth owner identity, and plugin activation;
   - `MAN-02` create and select an owner Page with trivia configuration;
   - `MAN-03` one sourced draft saved and retrieved;
   - `MAN-04` revision and approval with blocking quality evidence respected;
   - `MAN-05` content plan creation and schedule visibility;
   - `MAN-06` plan or post retrieval in a fresh conversation;
   - `MAN-07` copy-ready text and owner editorial review;
   - `MAN-08` ambiguous request causes clarification without an unintended write;
   - `MAN-09` unsupported auto-publication and malicious source instructions cause no forbidden action;
   - `MAN-10` after the owner genuinely publishes on Facebook, mark the corresponding post as posted without claiming the plugin published it;
   - `MAN-11` record genuine performance observations and request cautious insights, including an insufficient-sample caveat when applicable.
     Freeze exact wording and expected results in the guide before execution. Cards `MAN-01..MAN-09` use a designated owner-approved pilot Page and data that may safely persist; do not reset or delete production records to make tests appear clean. `MAN-10..MAN-11` remain `PENDING` until real events and data exist. No fabricated Facebook publication or metrics. All executed cards must pass; any unauthorized write, cross-owner exposure, secret leak, false external-action claim, or blocking-quality bypass stops acceptance.
5. **Two completion labels.** `Pilot-ready` means the Phase 9 technical and hosted gates pass, the final plugin is installed, and `MAN-01..MAN-09` pass, with no critical/high security or data-integrity defect. It authorizes a controlled owner pilot, not an MVP-complete claim. `MVP Complete` requires `MAN-10..MAN-11` on genuine pilot data, owner editorial approval, the applicable 14 PRD acceptance criteria evidenced, and Phase 11's backup/rollback, operational review, and handoff checks. Missing genuine publication or metrics stays `PENDING`. No fixed waiting period or 101-chat target is imposed.
6. **Evidence budget.** For each manual card, record the card ID, exact prompt, installed plugin version, conversation reference, selected tool names, observed outcome, a safe state reference, PASS/FAIL/PENDING, and a short reviewer note. Capture redacted arguments/results only when needed to resolve an ambiguity or defect. Technical CI artifacts and server request IDs carry detailed security/integrity evidence; the owner is not asked to inspect SQL, copy credentials, or collect exhaustive traces.

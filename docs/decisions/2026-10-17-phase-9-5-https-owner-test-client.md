# CR-024 — Proposed first-party HTTPS owner test client for Phase 9.5

Date: 2026-10-17  
Scope: checkpoint 9.5 only  
Status: **NARROW LOGGING EXCEPTION APPROVED; hosted dummy canary pending**

## Baseline and reason

The deployed MCP v4 is sourced from `8c94e515dc0952ba0939948071f18244db1bec9f` after technical gate #7 succeeded. The earlier hosted owner 401s were on MCP v3. CR-023 identified the internal Edge path mismatch, and a signed local regression passed after its fix. MCP v4 has returned 401 to missing and malformed credentials as intended, but has **not** received a fresh owner OAuth token in a hosted test. Therefore its owner result remains PENDING; the HTTPS callback proposed here is only a way to obtain and test such a token.

The previously approved public test client has only the exact loopback redirect `http://127.0.0.1:8745/callback`. Automatic browser security review rejected access to that callback. It will not be retried through another browser surface or indirect route. A separate first-party HTTPS client was requested for an official browser flow.

## Proposed design, subject to the logging blocker below

1. Register a **separate** owner-test OAuth client with exactly one redirect URI, `https://content-producer-auth-frontend.vercel.app/api/phase-9-5/callback`; no wildcard, preview domain, loopback URI, or alternate callback. Prefer a public client with `token_endpoint_auth_method=none` and PKCE S256; the server holds no long-lived OAuth client secret. Limit scopes to `openid email profile`. Keep the existing loopback client separate and revoke the new client after testing.
2. Add a feature-disabled-by-default Vercel server route for starting a test. Require and verify an existing Supabase browser session for the configured owner before it will start. Generate a fresh high-entropy `state` and PKCE verifier; place them in a short-lived, authenticated-and-encrypted `__Host-` cookie (`HttpOnly; Secure; SameSite=Lax; Path=/`) using a server-only key. The browser holds only ciphertext and cannot read the verifier through script. Redirect to the Supabase OAuth authorization endpoint with that **exact** redirect URI and an explicit `resource` equal to the canonical production MCP URL. Only the owner manually signs in and chooses Approve or Deny on the existing consent page.
3. The callback accepts only GET on the exact configured host/path. It rejects absent, duplicate, expired, or mismatched `state`, missing flow cookie, simultaneous `code` and `error`, or an unexpected OAuth error. It clears the flow cookie on every terminal outcome. A Deny PASS requires `error=access_denied`, matching state, and **no** code; a callback containing `code` is never Deny PASS.
4. On Approve, exchange the single-use code via the Supabase token endpoint with the original verifier and the exact registered redirect URI. Accept any successful 2xx response. Keep code, access token, and refresh token only in process memory for this request. Verify the returned JWT signature/JWKS, issuer, exact MCP resource audience, expiry, role, scopes, OAuth client ID, and subject equal to the configured owner UUID **before** any MCP request. Reject non-owner before calling MCP. No owner data, tokens, codes, or credentials are returned to the browser.
5. Run only MCP `initialize`, `tools/list` (exactly 33), `get_account_profile`, `get_workspace_context`, and `list_pages`. Reuse the already valid hosted MCP v4 no-token/malformed-token 401 evidence; do not copy these calls into the OAuth callback. Return a minimal result with HTTP status, safe error family, tool count, and per-read success flags. Never output tool response bodies or owner data. No `create_page`, post, publication, or metric calls. Send `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; redirect to a clean result URL after the callback.
6. Keep test endpoints disabled unless server-only configuration names the production Supabase issuer/resource, approved client ID, exact callback URI, and owner UUID. No privileged Supabase key or OAuth secret in the frontend bundle, build logs, source, or Issue. Use server-side request timeouts, bounded response sizes, fixed method/tool allowlists, and safe errors. Do not log request URLs, query parameters, headers, tokens, OAuth payloads, or MCP bodies in application code.

## Narrow exception: code in Vercel request metadata

The [Supabase OAuth 2.1 flow](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows) documents a GET redirect containing `code` and `state` in its query. Its documented authorization request parameters do not include a `form_post` response mode. [Vercel Runtime Logs](https://vercel.com/docs/logs/runtime) document **Search Params** in request details for function invocations, and [Vercel Log Drains](https://vercel.com/docs/drains/reference/logs) define `proxy.path` as the request path **with query parameters**. Removing the code from the browser address bar via a prompt 303 and omitting application logs does **not** prevent Vercel from observing or retaining the incoming query. PKCE and short code lifetime reduce misuse, but do not satisfy the owner's absolute requirement that the code is not recorded.

The owner explicitly accepts the possibility that a **single-use OAuth code for this Phase 9.5 HTTPS test client only** appears in Vercel's built-in request metadata. This is a narrow exception to the project's no-code-in-logs rule, **not** a claim that Vercel will or will not retain it. It does not authorize application logging, Log Drains for this route, browser rendering, Issue/report disclosure, or reuse for another OAuth client. Keep access to Vercel logs limited to the owner and the minimum operators needed for this test; do not share log exports. PKCE S256, short code lifetime, exact redirect, and immediate exchange reduce exposure but do not remove it. Revoke/delete the test client after the hosted test and record that action. The owner remains responsible for manual login and Approve/Deny.

Before registering the OAuth client or running real OAuth, deploy only a reviewed, gated, disabled-by-default candidate and send a **non-secret dummy** query to the callback path. Inspect Vercel's built-in request metadata and the project's configured drains/traces using a local comparison that outputs only presence/absence, never the dummy value. Do not enable a Log Drain. If the dummy appears outside the documented Vercel metadata boundary, or the inspection cannot establish the boundary, stop before real OAuth. Do not use a browser workaround, relay, second local callback, or unregistered redirect. The exact URI above is a proposed registration value until the canary passes.

The candidate sets Vercel `git.deploymentEnabled=false` so merging the source cannot auto-deploy before the required full technical gate succeeds on the merged main SHA. Deploy the frontend manually from that exact SHA only after the gate. The Phase 9.5 routes remain disabled without the server-only configuration; the disabled callback returns 404 to the dummy canary without parsing or reflecting its value. A passing canary permits exact-client registration and enabling the test route, but does not constitute any OAuth/MCP PASS.

## Controlled rollout and cleanup

1. Review source/CR and merge; run the full Phase 9 technical gate **once** on the final merged main SHA. If it fails, do not deploy. The previous v4 MCP deployment remains the hosted baseline; this change deploys the Vercel frontend only.
2. Manually deploy that exact SHA to the existing Vercel project with `PHASE95_ENABLED` unset. Verify the production callback returns 404 and the existing login/consent routes still work. Do not create a client yet.
3. Send one generated, non-secret dummy `code` query to the disabled callback using a local HTTP client, without printing its value or using a browser. Compare Vercel built-in request metadata and configured drains/traces in memory, emitting only boolean findings. Confirm drains remain absent and log access remains limited to the owner's team. Stop on unexpected propagation.
4. Register the separate public OAuth client with the one exact HTTPS redirect. Set server-only Vercel environment values `PHASE95_ENABLED`, `PHASE95_CLIENT_ID`, `PHASE95_OWNER_USER_ID`, `PHASE95_PUBLISHABLE_KEY`, and a random 32-byte `PHASE95_COOKIE_KEY` entered through a secure provider surface. Do not use browser-exposed `VITE_*` for these. Deploy the same gated SHA with the new environment; check enabled route and no source drift.
5. Guide the owner through a fresh Deny request **first**, then a separate fresh Approve request. The owner alone enters credentials and presses consent buttons. Record only redacted HTTP/status evidence. On a verified-owner MCP 401, stop the read gate and Page pilot, and diagnose the failing stage separately from the callback.
6. At the end of testing, delete/revoke **this HTTPS test client**, remove/disable its Vercel server-only settings, and redeploy the same source with the route disabled. Retain only status evidence and the narrow risk record. Do not remove the pre-existing loopback test client as an implicit side effect.

## Test plan and local evidence

- Unit: PKCE S256 challenge/verifier pair; fresh state and authenticated encryption of the flow cookie; exact redirect equality; reject absent/duplicate/wrong/expired state and missing/tampered cookie; reject simultaneous code/error; Deny only with `access_denied` and no code.
- Unit with synthetic signed JWTs: accept exact issuer/resource/client/owner/scopes; reject `aud=authenticated`, wrong signature, wrong client, expired token, and non-owner **before** MCP fetch.
- Contract with fake endpoints: authorization-code and refresh 2xx; initialize success; exactly 33 listed names; the three read-only calls; no-token and malformed-token 401; no write-tool calls; bounded responses; no sensitive values in body, headers, application logs, or result URL.
- Platform canary before any real OAuth code: use only a dummy query value on the disabled candidate callback, inspect Vercel Runtime Logs and any configured drains/traces for propagation. Appearance **within built-in Vercel request metadata** is the approved exception. Appearance elsewhere, or an inability to establish the boundary, stops real OAuth.
- Hosted after a safe callback path is approved and a new SHA passes the full gate: owner performs one manual login and consent action at a time; independently record the actual token 2xx, Deny, initialize, 33 tools, three reads, negative cases, function version, and redacted log evidence. Any 401 on a verified owner token stops the Page pilot and requires a separate MCP-layer diagnosis.

No production write or hosted 9.5 PASS follows from this design record.

Local focused tests use only synthetic codes/tokens/JWKS and mock endpoints; they exercise state/PKCE, exact redirect, owner gate, Deny with no token exchange, exact audience, 33-tool listing, and the three allowlisted reads. `pnpm run frontend:test` and `pnpm run check` passed after serializing frontend tests that otherwise wrote to the same build output concurrently. No heavy `test-all` or hosted canary has yet run on this candidate.

Read-only Vercel access review before deployment: project `content-producer-auth-frontend` is under the owner's personal team with one confirmed OWNER member; the project has **zero configured Log Drains**. Do not change that drain configuration or grant additional log access for this test. The hosted dummy canary must still verify the actual deployed route and built-in metadata before OAuth registration.

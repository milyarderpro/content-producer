# CR-028 — Phase 10 host-proof sequencing and per-card data binding

- **Date:** 2026-10-18
- **Status:** Accepted by the owner, pending repository merge after Phase 10 audit
- **Authority:** Owner explicitly approved revising the Phase 10 checkpoint order on 2026-10-18.
- **Supersedes:** Only the timing of write-entitlement proof, final package installation proof, and owner-data/prompt freezing in the Phase 10 runbook, PRD, tracker, and CR-027. All nine mandatory manual scenarios, existing security rules, and Phase 9/11 gates stay intact.

## Problem

The owner can open the ChatGPT Plus **Add custom MCP server** form with **OAuth** selected, but a particular tool's write availability or approval UI cannot be verified reliably before a custom MCP connection exists. Requiring that proof, a successful final-package installation, and complete Page/plan data selection at checkpoint 10.0 would force an OAuth connection, package install, or premature production decisions that 10.0 expressly forbids. Preflight evidence instead includes an independently downloaded and hash-checked GitHub Actions artifact and an account-accessible private plugin archive intake.

## Decision and checkpoint gates

1. **10.0 — read-only preflight.** Prove the owner's access to the private custom MCP creation form and OAuth selection. Prove the real **delivery path**, not an installed plugin: successful GitHub Actions artifact download and archive/hash verification, plus an account-accessible host intake capable of creating a **PRIVATE** plugin from a ZIP/tar.gz. Record the responsible downloader/installer and package identity limitations. Record owner-specific write entitlement as **PENDING FOR 10.1**, not a 10.0 blocker. Freeze all nine mandatory cards' **invariant rules, tool sequences, safety boundaries, approval points, state checks and recovery procedures** and maintain the optional cards' post-MVP status. Page, content, schedule and derived record identifiers remain intentionally unbound; **no owner input is needed merely to pass 10.0**. Keep one branch, one draft PR, evidence template, light CI, and no OAuth, new MCP connection, installation or business write.
2. **10.1 — first post-connection gate.** After creation of the owner-private custom MCP connection and successful owner OAuth, **before any ordinary owner reads or package work**, inspect the live tool registry for write tools including `create_page` and their permissions/approval affordances **without invoking any mutating tool**. Where possible, verify that a write action may request owner confirmation through read-only host UI/settings or non-executing tool metadata. A displayed `Write` annotation alone is insufficient; global permission defaults do not imply owner entitlement. **If a write-capable action or non-executing approval capability cannot be confirmed, stop 10.1 immediately with one specific host/permission diagnosis; do not proceed to a package.** If the host cannot expose approval readiness without an actual write attempt, record the limitation and stop rather than issuing a dry-run that could mutate state. Only then verify 33 tools and the three owner reads; no write in 10.1.
3. **10.2 — install the actual final plugin.** Prepare `mcp.json` only after 10.1 has passed, build and validate the final private archive, transfer it over the 10.0 delivery path, install it privately with owner action, and match installed version, archive SHA-256, skill and 33 MCP tools in a fresh chat. Delivery-path availability from 10.0 must not be called a final installation.
4. **10.3 `MAN-02` — first business write.** Before compiling or running MAN-02, ask the owner for the exact distinct new Page name/slug, IANA timezone, target markets, complete validated trivia config and `make_default`; present the final payload and obtain explicit owner approval. Then and only then invoke `create_page` once with a stable operation key through the authenticated owner MCP, followed by state/config/ledger verification. No SQL/admin workaround. The existing Phase 9.5 Page and key remain untouched.
5. **Just-in-time values for later cards.** Ask for the precise topic, format, profile, editorial constraints, and draft permissions immediately before MAN-03; seek a specific hook revision and review exact content/hash before MAN-04 approval; ask for a plan name, intent, and 1–3 exact scheduled slots immediately before MAN-05. Later cards bind previously verified Page/post/plan public IDs. Reconcile binding and approval with a dated ledger entry and exact compiled prompt _before executing that card_. No placeholders may be executed, no values may be silently selected by the agent, and user approval for one card is not blanket approval for later writes.
6. **Manual freeze distinction.** The 10.0 guide is a **frozen procedural template**, not nine executable fully bound prompts. Frozen per-card procedures and negative scenarios must not drift without revision/evidence. Exact prompts for value-dependent cards are compiled, frozen and recorded from approved real values **before the affected card is executed**. Review actual revisions/hash independently before editorial approval. Run each mandatory card once; rerun only failed or affected cards. `MAN-10..11` remain `DEFERRED — POST-MVP` under CR-027.
